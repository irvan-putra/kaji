What running it involves (from OpenBao's own docs)

  • Install. A single bao binary, distro packages, or container images from ghcr.io, quay.io or docker.io. install
  • Swap. OpenBao recommends disabling or encrypting swap so secrets in memory are not written to disk. install
  • Storage and backup. Integrated Storage (Raft) keeps data on the server's disk. bao operator raft snapshot save writes a backup and restore installs one. Snapshots are not supported if Raft is used only for HA storage. integrated storage, operator raft
  • Unseal depends on the seal method. The server starts sealed. With the default Shamir seal, a threshold of key shares must be entered by hand after each restart; the docs call automating that a discouraged pattern. Auto unseal methods avoid the manual step. seal
  • Auto unseal. The built-in static seal reads a 32-byte key from a file or environment variable. OpenBao warns it fits mainly where another trusted secret source already exists, because that key sits next to the server. Other seal methods use an external KMS or HSM. static seal
  • Break-glass. A lost root token can be regenerated, but only with a quorum of the unseal key holders (operator generate-root). Lose the shares and the data is gone. generate-root
The real tradeoff. Manual Shamir unseal needs a human after a reboot. Auto unseal removes that, but moves trust to the key file or external service. Backups must include something that lets you unseal, kept apart from the backup itself. A single small server is also a single point of failure for every app that depends on it.

Part 2. If an app or bot secret leaks: a generic recovery plan

This checklist is generic reading material. It is not standing permission for me to revoke real credentials, change accounts or stop a running app. Each of those would need your go-ahead when it happens.

This applies today, with or without OpenBao. The key point, from GitHub's own guidance: treat a leaked secret as compromised. Deleting it from the file, making a new commit, or deleting the repo does not undo the exposure. The fix is to revoke it at the service that issued it. GitHub: remediating a leaked secret

The steps, in order

  1. Stop the spread. Pause the app or bot if it is safe to. Do not paste the secret anywhere else, including chats.
  2. Identify it. What kind of secret, which service issued it, where it leaked, whether it was public, and what it can do.
  3. Revoke at the issuer. Use the issuing service's own settings. If the service needs the old one to keep working, create the replacement first, switch the app, then revoke the old. For GitHub, personal access tokens leaked in public repos are revoked automatically, and private ones can be reported from a secret scanning alert. same GitHub page
  4. Replace. Make a new secret with the smallest permissions that work, and store it only in the app's secret store (for example a repo Actions secret), never in code or chat. GitHub: Secrets
  5. Check for use. Look at the issuer's logs for activity you did not do, from the time of the leak. Rotate anything the attacker could have reached with it.
  6. Clean up and note it. Remove the secret from files if it is still there, and write a short dated note: what leaked, what was revoked, what was replaced, what was learned. Keep the note free of the secret itself.

Keep the next leak smaller

  • One secret per app, so a leak costs one rotation.
  • Smallest permissions, and expiry dates where the issuer supports them.
  • Turn on secret scanning and push protection where available (free for public repos per GitHub's page above).
  • Keep an inventory of secret names and where each is revoked, never the values.
