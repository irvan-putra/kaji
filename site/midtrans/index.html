Midtrans agent skills: guidance, not a payment account

Midtrans publishes a beta set of instructions for coding assistants working on merchant payment integrations. It can help developers choose and implement a payment flow. It is not a merchant account, approval to accept money, or a live payment connection.

Public-source explainer checked 21 November 2026. Merchant eligibility, payment methods, rates and payouts depend on the actual business and approved account. This page does not collect payments or ask for credentials.

What the official project provides

The veritrans/midtrans-agent-skills repository is linked from Midtrans's official AI integration documentation, which labels agent skills as beta.

The repository describes guidance for Snap hosted checkout, Core API, BI-SNAP, QRIS, virtual accounts, GoPay and other merchant flows. It helps a coding assistant inspect an existing application, choose the relevant product path, adapt integration code and plan sandbox verification. Its documentation also covers notifications, signatures, refunds and go-live operations.

No MCP server ships in this phase. The README describes authenticated API tooling as a future, separate phase. Reading the Markdown guidance needs no merchant credentials and does not itself call payment APIs. Implemented code or helper scripts can have effects when separately configured and executed; do not confuse a reference document with a harmless guarantee for everything in a repository.

This note describes the vendor project, not an installed integration. No installation command is needed just to understand the choices.

Three ways to accept a customer payment

RouteBest starting needWork still required
Payment LinkSend someone a link to pay for a named product or service.Merchant activation and enabled payment methods; create a link in the dashboard. Midtrans hosts checkout. No technical integration required.
SnapCheckout within a website/app using Midtrans's hosted payment interface.Backend transaction creation, secure credentials, order records and verified payment notifications; sandbox and production are separate.
Core API / BI-SNAPMore direct control over a supported payment flow.Product-specific API implementation, authentication, customer experience, state handling and operational testing. More engineering, not a shortcut around merchant approval.

Payment Link documentation describes creating a link with a product/service name and price, with optional customer, expiry and usage controls. A customer opens Midtrans's hosted checkout and follows payment instructions. For an initial, occasional sale, this is a smaller technical step than building custom checkout.

Can an individual merchant receive money?

Yes, Midtrans advertises registration for individual businesses as well as legal entities. That does not mean every personal transfer, donation, industry or business model is approved.

  • The official homepage lists KTP for Indonesian individuals or KITAS for foreign individuals. It says NPWP is needed for activating methods beyond GoPay, QRIS and bank transfer. Other methods or business categories can need additional documents.
  • Payout bank details must match the entity: an individual uses the merchant owner's personal-name account; PT/CV merchants use the entity-name account.
  • Registration guidance requires a publicly accessible website, application or social-media URL showing the product and price. An empty Hello World page does not show a product and price.
  • Real-payment activation includes business information, legal documents and agreement to applicable terms. Enabled payment channels and approval must be checked in the actual account.

Before selecting a route, establish what is being sold, who the customers are, the merchant's legal form and required payment methods. Then confirm eligibility and documentation with Midtrans. A sandbox simulation is not production approval or proof that a real bank payout will work.

The official pricing page, checked 21 November 2026, says setup is free and fees apply to successful transactions. Selected published rates:

Official tax wording differs between pages. The current pricing page says fees exclude VAT except QRIS, GoPay and ShopeePay. An older fee FAQ instead says all fees exclude VAT and gives an 11% VAT example. Do not turn that older example into a universal current tax rule or promise an exact net receipt. Use the current pricing page as the public rate reference, then confirm the actual channel's tax treatment and merchant contract before going live.

The FAQ says no implementation or maintenance fee and no additional Core API service charge. Custom development, hosting, refunds, disputes, special categories and negotiated commercial terms still need their own check; this page is not a complete cost quotation.

Payment success is not instant bank availability

Midtrans's withdrawal FAQ says funds can be withdrawn at least three business days after a transaction, subject to completed registration documents, bank details and a successful/settlement transaction. It lists no additional withdrawal fee, a Rp10,000 minimum payable amount for withdrawal and Rp50,000 for automatic withdrawal.

The same FAQ describes an 11am cutoff, working-day schedules and banking-holiday delays. Treat that as published general guidance, not a guaranteed payout date for every channel. Confirm settlement availability, the withdrawal schedule and bank arrival timing in the merchant's current terms. Refunds and disputes also need an operating process.

If an integration is built later

  1. Choose the commercial flow. Named service/product, price, refund terms, merchant entity and payment channels first. Use Payment Link if custom checkout adds no value.
  2. Keep sandbox separate. Test fake payments without treating them as income. Live keys and production activation are different steps.
  3. Keep server credentials on the server. Never put a Server Key into public HTML, a mobile app package or a repository. Use separate sandbox/production configuration.
  4. Verify payment state server-side. Authenticate notifications and reconcile with Midtrans status. Do not release goods or services merely because a browser reaches a success page. Handle duplicate, delayed and reordered notifications safely.
  5. Prove the whole path. Order creation, cancellation/expiry, settlement, refund handling and bank reconciliation are distinct checks. Enabling real transactions is a separate approved step.

Key handling has changed: the current Access Keys documentation says notification signatures use a separate Signature Secret Key since 28 October 2026. Older examples still refer to a Server Key. Check the current product-specific documentation instead of copying an old signature recipe. Both secrets belong only on the server.
