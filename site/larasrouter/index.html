Laras Router: a model API gateway with a QRIS wallet

Laras Router is an Indonesia-facing API gateway for supported third-party language models. Developers call a common interface and pay from a USD-denominated wallet funded through QRIS. It is not its own foundation model or a general chatbot subscription.

Compatibility has a boundary

The current docs describe OpenAI-compatible Chat Completions and Anthropic Messages compatibility. They explicitly say the OpenAI Responses API used by Codex CLI is not yet supported. Do not read OpenAI-compatible as every client working unchanged.

The word router does not establish automatic cheapest-model selection or guaranteed failover. No API call, key creation, account signup or client integration was tested here. Listed streaming, tool calls, JSON output and large context limits are vendor feature claims, not verified model behavior.

QRIS top-up is not the same as token cost

Public pages say top-ups are $1–$100 per payment. Conversion uses the vendor's exchange-rate buffer, described as about 2%, plus a separate 1% administration fee that does not become wallet credit. The actual IDR amount must be checked at checkout.

The current homepage says no free trial credit. The noticeboard's earlier first-20-user bonus remains an unverified historical note, not an available offer. Do not create an account expecting free usage.

Purchased credits are described as non-expiring, but also non-refundable, non-withdrawable and non-transferable. Account closure forfeits the balance. These conditions matter even when the smallest top-up looks inexpensive.

A key budget is not a hard zero-overrun guarantee

  • The billing docs describe soft per-key limits and admission checks. Requests admitted before a limit is reached can push usage past it.
  • The wallet can overdraw by up to $1, settled on the next top-up according to the docs.
  • Do not assume failed requests are always free. The legal terms allow charges for upstream usage on some server errors, timeouts or interrupted responses, even where a shorter guide simplifies failure billing.

Data passes through more than one party

The privacy policy says gateway prompt/response content is processed transiently in memory, not persisted or used for its training. That is a vendor claim, not an independent retention audit or a promise covering upstream providers. Requests go to external model providers with separate terms and possible retention outside Indonesia.

Account/usage metadata, diagnostics, analytics and billing records are separate from prompt content; the policy describes financial-record retention of five years. A transient-content claim is not end-to-end zero retention and does not make secret-bearing prompts safe.

Before an integration

  1. Check endpoint/protocol compatibility and the selected model's current features.
  2. Review provider data rules and remove personal/customer/secrets from any first test.
  3. If spending is separately approved, confirm the final top-up total, budget-overrun rules and non-refund conditions. Start with synthetic inputs and inspect per-request metering.

No signup, key, model call, top-up, payment or software install was made. Vendor latency claims were not independently benchmarked.
