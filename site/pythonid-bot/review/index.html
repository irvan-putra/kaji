PythonID-bot: contribution ideas

Options review only. Nothing here is built, committed or decided. PythonID-bot is Rezha's Telegram moderation bot for the PythonID community (profile checks, captcha for new members, layered anti-spam, AI-assisted spam monitoring). The repo is private at the moment, so this page stays high-level on purpose and no internals are quoted.

Short answer. The project is already well tooled: CI across five Python versions, strict-ish typing, property-based tests, Dependabot. The natural first contributions are the few remaining coverage gaps and a contributor guide (marked recommended). Anything that changes moderation behavior or adds a feature needs Rezha's agreement on shape before any code is written. Nothing is pushed without Irvan approving the exact change first.

A. Ready now - small, standard, low risk

Five service modules sit between 70% and 95% line coverage (text-formatting helpers, the scheduler, rich message rendering, captcha recovery, admin cache) while the project aims for full coverage. Pure test additions, no behavior change.

Effort: small-medium · Risk: low · Buy-in: not needed. Deliberately tests only.

CI runs the tests but does not enforce a coverage floor, so coverage can silently regress. Add a fail-under threshold at roughly today's level.

Effort: small · Risk: low · Buy-in: the threshold number.

There is no contributor guide: setup with uv, the test/lint/type commands, and PR conventions currently live only in agent-facing docs. A short human-facing guide lowers the bar for the next community contributor.

Effort: small · Risk: low · Buy-in: Rezha may want the conventions in his own words.

The project already uses Hypothesis. The vendored Markdown escaping/mention helpers are pure functions with stable output, a natural fit for round-trip and never-crash properties.

Effort: small · Risk: low · Buy-in: not needed. Folds into A1 if preferred.

B. Features - need Rezha's buy-in on shape first

Guest-bot strikes currently sit outside the self-service unrestriction flow by design; an admin-side command to review and clear them would close that loop without changing the deliberate default.

Effort: small-medium · Risk: low · Buy-in: command shape. Deliberately admin-only.

The AI spam monitor is monitor-only and posts alerts with action buttons. Letting admins mark a false positive from the alert, recorded for threshold tuning, would close the feedback loop.

Effort: medium · Risk: medium · Buy-in: definitely. Deliberately keeps the monitor non-enforcing.

A scheduled per-group summary for admins: warnings issued, captcha completions and timeouts, spam deletions. The data already exists in the bot's database.

Effort: medium · Risk: low-medium · Buy-in: feature.

C. Docs and community

The bot's interface and community are Indonesian; the README is English-only. An Indonesian translation next to it fits the audience.

Effort: small · Risk: low · Buy-in: not needed.

The repo has thorough agent-facing docs; a short human-readable architecture map (plugin system, handler order, where to add what) would serve new contributors.

Effort: small-medium · Risk: low · Buy-in: not needed.

Deliberately not proposed

  • Framework or architecture changes: the aiogram 3 migration just landed and the plugin system is fresh.
  • Turning the AI spam monitor into auto-enforcement: monitor-only is a deliberate design choice.
  • Changing warning thresholds, probation length or other community policy: that is group governance, not code.
  • More CI or dependency automation: the matrix is broad and Dependabot is already active.

Decided

Irvan's pick, 24 Nov: follow each project's own contribution rules. Commit and PR wording will follow the project's own norms for AI-assisted work, and nothing will state or imply human authorship either way.

Applies to every option on this page. Deliberately settled before any code.
