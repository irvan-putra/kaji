mobile-agent-testers: 20 AI testers on 20 phones, and what it could do for our apps

An MIT-licensed GitHub Actions workflow. Each tester is a Claude Code agent with its own Android emulator or iOS Simulator and a persona (language, font size, device). It uses the app and writes a bug report with screenshots.

Status: read from the public repository on 25 Nov 2026. Nothing was installed or run, and no tester has touched any of our apps yet. Numbers below are the author's, not ours.

What it is

  • Source: https://github.com/pierridotite/mobile-agent-testers (MIT, author Pierre Raffalli per the LICENSE file).
  • Runs in your own repository on GitHub's runners. The runners are free for public repos; you pay for the model, which the README puts at about $0.15 to $0.55 per phone.
  • Modes: explore like a new user (default), run one feature end to end from your own brief, reproduce a bug report on every phone, write an improvement report per persona, compare two builds.
  • Supports Flutter, React Native/Expo, native Kotlin and Swift, Kotlin Multiplatform, Capacitor and .NET MAUI, or any build command that produces an APK or simulator app.
  • 20 ready personas: 14 languages, right to left, tablets, text sizes up to the largest accessibility setting. Personas are plain JSON in personas.json.
  • Results are encrypted with your public key before upload; collect.sh decrypts and groups duplicates. Its PRIVACY.md says the project has no server or analytics.

What we could do with it

1. Test our Android APKs

Most of our apps ship as APKs from public repos (Kapan, Tuju, Tumbuh, Kokok and others, see the APK page). One tester per persona on Android only would cover small phones, 200% font and dark mode. iOS is not needed, which also avoids macOS runner costs.

2. Indonesian personas

The built-in 20 have no Indonesian-language persona that we confirmed. Adding one or two (id-ID, Jakarta geo, cheap phone, one-handed on the busway) is a small edit to personas.json, and fits Tuju and Kapan best.

3. Feature briefs

A custom brief can send every agent through one flow, for example adding an alarm in Kokok or a countdown in Kapan, then relaunching to check it was saved. That finds the cut-off-by-keyboard class of bug a unit test misses.

4. Compare two builds

Same personas on two branches gives a table of goals reached and issues seen on one version only. Useful before a release such as a Tuju version bump.

5. A cheaper model

The repo documents Haiku and any Anthropic-compatible API (Qwen via DashScope is listed). The model must read images. Fenrir's Qwen route has not been tried here, so whether it accepts this protocol and screenshots is unknown.

What stops us today

  • New repo: the quick start creates a repo from the template. Our rule is no new repos without Irvan's yes, and the alternative is copying the workflow into an existing repo.
  • A model key: it needs a Claude token or an API key as a GitHub secret. Nothing is stored for this yet.
  • Spend: a first pilot would be one app, two Android personas, about $0.30 to $1.10 at the README's per-phone range. Not run.
  • Public run inputs: run inputs are public on a public repo, so build keys go in secrets, per its configuration doc.
  • AI disclosure: any bug found this way would be AI-reported and unreviewed, and should be labelled that way.
  • The author is also exploring a paid hosted version. The workflow itself is stated to stay free and open source.
