startup-class/setup: a 2013 EC2 setup script, read

A small repo from the Startup Engineering MOOC that turns a fresh EC2 Ubuntu box into a working dev machine with one script. Read on 25 November 2026, not run.

Source: startup-class/setup ("AWS EC2 setup files for Startup Engineering MOOC", created 1 July 2013, shell; 294 stars and 1,224 forks when checked). Two files only, README.md and setup.sh. No license file is in the tree, so we read it for ideas and copy nothing.

How it is meant to be used

cd $HOME
sudo apt-get install -y git-core
git clone https://github.com/startup-class/setup.git
./setup/setup.sh

The README targets Ubuntu 12.04.2 LTS on EC2 and points to the companion dotfiles repo.

What setup.sh does, in order

StepWhat it does
BasicsInstalls git and curl with apt.
NodeInstalls nvm with a curl-to-sh line, then installs and selects Node v0.10.12.
JS toolingInstalls jshint globally with npm, and rlwrap for a nicer node REPL.
EditorAdds a PPA, then installs emacs24 (terminal-only build).
Deploy toolInstalls the Heroku toolbelt with wget piped to sh.
DotfilesClones the dotfiles repo, moves any existing dotfiles and .emacs.d aside, then symlinks .screenrc, .bash_profile, .bashrc, .bashrc_custom and .emacs.d into the home folder.

The idea worth keeping: tools and personal config come back from one repo and one command, so a throwaway cloud box is cheap to lose.

What has aged (observed in the file, not tested)

  • It targets one Ubuntu release from 2013 and Node 0.10.12, both far behind today's versions.
  • The nvm install uses a raw.github.com address and an old project path. The Heroku toolbelt and the emacs PPA are third-party sources that may no longer exist.
  • Two steps pipe a downloaded script straight into a shell, with no checksum or pinned version.
  • No set -e, so a failed step does not stop the script, and nothing reports which steps worked.
  • Backups use mv dotfiles dotfiles.old. On a second run dotfiles.old already exists, so the move would behave differently. This is a reading of the code, not a run.

What we take from it

  • Keep machine setup in a script in a repo, not in memory.
  • Keep personal config in a separate repo from the install script.
  • Pin the versions you depend on and write down the OS the script was written for.
  • Make the script safe to run twice, and stop on the first error.
  • Download and read a script before running it, instead of piping it into a shell.
