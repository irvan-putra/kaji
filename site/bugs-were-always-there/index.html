The Bugs Were Always There: an IDSW 2026 keynote, checked

Talk reading, 22 Nov 2026. Sixty photos of Eko Kurniawan Khannedy's keynote slides were visually inspected, through the thank-you slide numbered 71; the set has gaps and is a partial photographic record, not a transcript. The speaker's name is printed on the closing slides. Slides are in Indonesian; quotes are our translations. Original photos are not reproduced, and the speaker's research results are attributed rather than re-derived.

The pattern: from suspicion to a small proof

Some bugs are easy to suspect and hard to show. Two requests can read the same balance. Two APIs that look reasonable on their own can make one page call too much. A system that looks cheap per month can be expensive per completed job. The keynote's invitation is to use AI help to prepare reproductions, simulations and analyses, while keeping the burden of proof: an AI's explanation is not evidence, and an illustrative graph is not a measurement.

  1. State a suspicion that could be wrong.
  2. Define the correct condition that must always hold.
  3. Build the smallest experiment that could show the condition breaking.
  4. Run it, keep the result, and check the experiment really tests the suspicion.
  5. Change the design or code, re-run, and write down the limits of the conclusion.

Example 1: one balance spent twice

The speaker's diagram shows two requests both reading a Rp100,000 balance before both write Rp50,000. The drawn final balance is Rp50,000, although two Rp50,000 purchases should have emptied it. The useful proof is not naming "race condition": it is building an execution schedule that forces both reads to happen before either write. After a fix, the same schedule must pass. Passing one schedule does not prove freedom from races under all conditions.

Example 2: review the request journey, not one API

The slide example shows a frontend fetching a product list, then fetching each product's details one by one: one list call followed by N detail calls. Reviewing each endpoint separately misses the combined pattern. Before choosing a batch API, a cache or a response-shape change, count the calls in one user journey, and check response sizes, access rights, the data actually needed, and contract-change risk. An AI's suggestion of a better API still has to be tested against real callers.

Example 3: cheap per month is not the same as efficient

The slides compare apps by monthly bill, then shift to cost per request. The lesson is to check the divisor before calling the bigger bill the wasteful one: use cost and request counts from the same period and scope, state whether shared costs, failed requests, retries and background jobs are counted, and remember that cost per request is not the only measure of value, since one app's request can do very different work from another's. The slide's own per-request figures rest on request divisors we did not receive, and its rounded ratio does not divide cleanly (the displayed integers give about 14,478, not the slide's 14,400), so this page does not reuse those numbers; the Sanggup exercise uses fresh synthetic ones.

The easily confused part: stateless queue positions

The first queue design stores an answer per person: this registration number gets that position, and at opening time every browser asks the server to look up its row. The discussed alternative replaces the position table with a repeatable calculation from the registration number and the draw settings, so the browser can compute the displayed position without a per-person position lookup at opening time. "Stateless" applies to that position-calculation part, not to the whole system: the same slides still have server-signed tickets tied to a session and registration number, and registration, eligibility, authentication, ticket validation and duplicate-use prevention are separate concerns the photos do not fully specify. Zero position lookups at opening is not zero server traffic.

The step before the mapping is also unresolved in the photos: they do not show who issues the registration numbers, when, or how their uniqueness is enforced. The ten-person diagram starts with numbers that already exist, and the CDN slide says only that everyone receives the same document, without specifying its contents. We therefore do not claim the CDN issues numbers, distributes the algorithm, or shares a key; the photos support a common document plus browser-side position calculation, without the bridge between them. The slides' context is a ticket war, where many people try to buy at the same time: issuing unique inputs while that surge arrives is a different question from computing positions once the inputs exist, and the photos address the second, not the first. An attendee's account of the talk adds the spoken context: registration numbers are issued through the usual process before the exact opening time, and at opening the CDN delivers the key, so browsers can calculate positions without a per-person lookup. That account is consistent with the slides but is not itself visible in the photos, and the security and fairness of the implementation remain unverified.

Feistel is the mapping idea the speaker named. His ten-person example shows positions 1 to 10 each appearing once, which demonstrates the intended output shape, not the fairness of the draw, its security, or its capacity at a million users. A unique mapping is not the same as a draw that cannot be manipulated, and the name "Feistel" alone guarantees neither.

What we keep

Ask AI to challenge your assumptions, then turn the challenge into a test. Inspect the boundaries between systems, not only the systems. Make evidence-gathering a small routine. Conclusions should follow what was actually observed, not the size of a claim on a slide or a model's confidence. Sanggup carries the practice versions in the Coding path: "Make the race condition show up", "Count the calls in one user journey" and "Decide what still needs remembering".

Limits

  • Partial capture: 60 inspected photos with known gaps (including around the cost example and the mapping mechanism); missing slides were not reconstructed.
  • Feistel result numbers remain the speaker's, unreproduced; opening-time plots are illustrations; a million-person queue is a scenario assumption, not measured traffic.
  • Nothing here endorses hand-rolled production cryptography; the NIST draft is cited for caution, not as an assessment of the talk's construction.
