Remote Browser: a fleet of browsers, not another AI model

An open-source service for launching and controlling remote Chromium or Chrome browsers. Automation code connects to them; each browser runs in its own virtual machine.

The useful distinction: Playwright or Puppeteer tells a browser what to do. Remote Browser supplies and manages the browsers those programs connect to. An LLM can be added to its Playground, but it is optional, separately configured and not a guarantee of safe automation.

Good fit

Running separate browser sessions for automated testing, scripted research or browser-controlled workflows when a single local browser is not enough. The service handles launch, status, suspend, resume and termination.

Not what it does

It is not a language model, a general website-hosting platform, or permission to act in somebody's account. It does not establish that an automation is correct, that a site permits it, or that a website will accept automated traffic.

What the repository actually documents

API and automation

The REST API manages browser instances. Programs drive a running browser through a Chrome DevTools Protocol (CDP) WebSocket, including Playwright's connect-over-CDP route. API calls and CDP connections require Bearer authentication.

Workspace API keys have expiry choices and are shown only once. The service stores a digest, not a recoverable copy. Keys and browser-session data should be treated as credentials.

Node.js and Python SDKs

Official SDK documentation names @remotebrowser/sdk for Node.js 22+ and remotebrowser for Python 3.11+. They wrap the API and take a server URL and an API key. The server package itself currently requires Node.js 22.12 or later.

This page links to the documented routes; no package was installed or executed for this review.

Keep or end a session

Suspend saves the VM state and releases its running memory. Resume restores the session. Terminate stops it and removes its machine directory. Persistent VM storage is needed for sessions to survive a host restart.

Those operations have different consequences. Terminate is not a pause, and restoring a logged-in browser can restore access to an account.

Optional natural-language harness

The Playground can send a task and the open page's accessibility tree to an OpenAI-compatible chat-completions service. That service writes a script; Remote Browser checks it before running it. Without an LLM, the Playground still accepts scripts.

The project explicitly warns that script verification is not a sandbox: a permitted script still controls the browser. Page content and task text go to the configured model provider unless a local model server is used.

Self-hosting is the real requirement

The current quick start for Linux needs KVM access, Docker and PostgreSQL. Running from source also requires QEMU, a C compiler and other host tools. The development setup can fall back to embedded PGlite when no database URL is supplied; the production guide requires PostgreSQL configuration.

Hardware access

Linux uses QEMU/KVM. The documented macOS source route targets Apple silicon with Hypervisor.framework. This is more than serving a Node.js web app: check the host's virtualization support before choosing infrastructure.

Default configuration is two virtual CPUs and 4G of memory per browser VM. These are configuration defaults, not measured total-host requirements or a concurrency guarantee. Memory and simultaneous VM starts can limit the fleet.

Production operations

The production guide requires a public HTTPS origin, session/resource secrets, database connection and SMTP-based sign-in configuration. Keep VM data on persistent storage and plan updates, monitoring and backups.

The local quick start exposes a Docker socket to build VM images. The project's own warning says that socket gives full control of the host. Production guidance instead builds the image separately, then runs the service without that socket.

Isolation has boundaries

  • The design gives every browser its own VM instead of sharing the host kernel. That is the project's architecture, not a claim that escapes are impossible.
  • The sandboxing guide says VMs can still reach other hosts on the network. Use a host firewall or upstream proxy where network access needs restriction.
  • CDP and QEMU VNC are intended to remain on host loopback. The documented VNC server has no password, so exposing it is unsafe.
  • Untrusted page content can steer a model. Checking a script does not make an unauthorized click, message, purchase or disclosure acceptable.
  • No security audit, production installation, throughput test or independent performance benchmark was performed for this page. The documentation's stronger isolation/performance language is not repeated as a measured result.

Cost and license

The repository is labeled AGPL-3.0-only. Open-source code does not include free compute, storage, network traffic, SMTP, proxy service or model inference. No hosted-service tariff was verified in this review.

AGPL is a copyleft license. Section 13 specifically addresses modified versions used over a network and an offer of their corresponding source to remote users. Review the actual license and your deployment/distribution changes rather than treating it as a permissive license or assuming every use has identical obligations.

A sensible first evaluation

  1. Read the getting-started and production guides before selecting a host. Confirm virtualization access, persistent disk and enough resources.
  2. If deployment is separately approved, begin with a disposable browser and a non-sensitive test page. Keep production credentials and real customer data out of the first test.
  3. Test lifecycle, authentication, isolation and cleanup before introducing an LLM. Keep human approval around consequential actions.
